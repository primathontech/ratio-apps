# Learnings (cross-cutting gotchas)

Non-obvious facts discovered while building. Newest first. Add via the `remember`
skill. Keep each entry 1–3 lines.

- **2026-07-31** — The `/<slug>/api/` write bucket in `main.ts` is **20/min per IP**, which silently assumes one user action ⇒ one POST. Any **chunked/fan-out route** (bulk CSV row ingest: `ceil(rows/chunk)` POSTs) blows through it mid-operation and 429s partway, leaving a half-ingested job. Such routes need their own `classify()` bucket — keep it **IP-keyed**, never merchantId-keyed (the Authorization header is attacker-rotatable — S1). Pair it with a chunk size checked against Fastify's 1 MiB `bodyLimit` × the row's max field sizes, or the same flow 413s instead.
- **2026-07-31** — When a client mirrors server validation for a **preview**, the two must be exact ports, not "close enough": a looser client phone regex made the loyalty CSV preview promise rows the server then rejected, **and** miscounted duplicates (`9876543210` vs `+919876543210` read as two customers, inflating the coin total). Normalize to the canonical form **client-side** so previews, dedupe and totals agree with what will be written.
- **2026-07-31** — An enum value declared in a DB types file is **not** evidence anything writes it. Loyalty's `firstSeenSource` had `'bulk'`/`'manual'` declared but unwritten, so bulk/manual credits ran a mirror `UPDATE` matching zero rows: Core held the coins while the customer was absent from every admin screen — reading to the merchant as "the credit did nothing". Grep for actual writers of each enum member before trusting it as a code path.
- **2026-08-04** — **CleverTap catalog sync is a full-replace CSV upload, not a per-item push.** The Catalog API is 3 steps: `get_catalog_url` → `PUT` the CSV to the returned URL → `upload_catalog_completed`; auth = `X-CleverTap-Account-Id` + Passcode; mandatory CSV columns are `Name`/`ImageURL`/`Category`; there is **no per-item endpoint**, so every sync re-uploads the whole catalog. The product-list source is verified at `GET /api/v1/v1/products?limit&page` on `RATIO_API_BASE_URL` (note the doubled `v1/v1`), auth = merchant OAuth bearer (`READ_PRODUCTS` scope), Shopify-shaped `{ products[], pagination{ hasNext } }`. Wired end to end (RatioProductSourceClient, 3-step uploadCatalog client, buildCatalogCsv, catalogName/catalogEmail/catalogSyncEnabled config + admin form, ClevertapCatalogSyncService, debounced dirty-scheduler off `products/*`), but sync stays gated on `CLEVERTAP_CATALOG_CONTRACT_VERIFIED` until a live upload is confirmed. Never log the decrypted Passcode.
- **2026-07-29** — ⚠️⚠️ **The OFFICIAL platform webhook docs are at `https://sandbox-developers.dev.gokwik.in/docs/webhooks/{overview,topics,verification}` — read them FIRST; they settle payload shapes definitively and they contradict several of our assumptions.** (a) **Payload shape is PER-RESOURCE and MIXED:** `orders/*` FLAT (order fields at top level), `customers/*` FLAT, `loyalty/*` FLAT, but `products/*` wrapped in `product`, `collections/*` in `collection`, `reviews/*` in `review`. So `core`'s `envelopeResource()` = `(e.product ?? e.order ?? {})` works ONLY for products — orders/customers/loyalty all yield `{}`. (b) 🔴 **ORDER MONEY IS RUPEES, NOT PAISE** — decimal strings (`total_price: "1200.00"`, line-item `price: "600.00"`). `products/*` IS paise (2026-06-22). Two different units on two resources; dividing order amounts by 100 under-reports revenue 100×. (c) **`customer` / `shipping_address` / `billing_address` are NULL when not supplied**, with `email` + `phone` at the ORDER top level — so identity must read top-level first. (d) **Respond 200 within 5 SECONDS** (not 10) and the docs say process asynchronously — an inline vendor call inside the handler risks the platform timing out and retrying. (e) **Retries: 5 attempts** — immediate, 1m, 5m, 30m, 2h, then failed. (f) All **8** order topics deliver the IDENTICAL full order object; only values and `event_type` differ. (g) **"Only the topics listed are delivered. The registration API may accept other topic names for compatibility, but subscribing to an unlisted topic produces no events."** — `app/uninstalled` is NOT listed. (h) ⚠️ **The signature scheme now has FOUR conflicting descriptions** across our guard, learnings, the Bluedart TRD, and these docs (`X-Ratio-Signature`, raw body, `sha256=<hex>`, app webhook secret from `/applications/{appId}/credentials`) — the TRD explicitly calls the docs' scheme *stale*. Unresolvable by reading; build a permissive guard that logs which combination validated.
- **2026-07-29** — ⚠️⚠️ **The VERIFIED platform webhook contract lives in `update/Bluedart - TRD.md` §4.0 (marked os-devecosystem-verified, synced from the Delhivery build). Read it before trusting `core` or the public dev-docs — core is wrong on two counts.** (1) **Signature:** header **`X-Webhook-Signature`** with `X-Webhook-Timestamp` + `X-Webhook-Id`; signature = `HMAC-SHA256(secretKey, "${timestamp}.${rawBody}")` — Stripe-style, **not** the raw body alone — and the secret is the **per-subscription `secretKey`**, not `client_secret`. The TRD says the public dev-docs' `x-ratio-signature`/raw-body scheme is **stale**; our `core/webhooks/webhook-signature.guard.ts` (`x-ratio-hmac-sha256`, raw body, `client_secret`) is wrong in all three dimensions and only "works" because absent-header requests are skipped off-production. Digest encoding hex-vs-base64 still unconfirmed (TRD K12). (2) **Order payloads are FLAT** — order fields plus top-level `event_type`/`merchant_id`, **no `order` wrapper** — whereas `products/*` IS wrapped in `product`. `core`'s `envelopeResource()` returns `(e.product ?? e.order ?? {})`, so a flat order yields `{}` and **every `orders/*` handler in the repo silently receives nothing**. (3) `orders/paid` is the purchase trigger — there is **no `order.confirmed` event**. (4) COD is **derived**; there is no dedicated COD field, and the platform's own `CreateOrderDto` declares **`payment_gateway_names` (an array)** — singular `payment_gateway` does not exist. (5) Test gotcha: **manually marking an order paid does NOT emit `orders/paid`** — a real checkout order is required.
- **2026-07-26** — ⚠️ **KwikPass auth is NEVER published on the OpenStore pixel bus — a `metadata.user_data`-only identity bridge identifies nobody at the OTP moment.** `meta-pixel.ts` says so twice from live experience and is the only correct reference. Identity actually comes from three places: **`window.__openstore_user`** (the storefront's canonical published PII — `{email, phone, first_name, last_name, external_id}`), an **origin-gated GoKwik `postMessage`** (`/(^|\.)gokwik\.(co|com|in|io)$/i`, types `otpVerifiedGk` / `kp_token`, and cart messages carrying `email`/`phone` which meta-pixel copies INTO `__openstore_user`), and the **`user-loggedin` / `user_loggedin_merchant` window CustomEvents**. The origin regex is a **security control** — never accept identity PII from another origin. Token keys + cookie-before-localStorage lookup live in `packages/loyalty-sdk/src/kwikpass.ts` (localStorage reads must be try/caught — Safari private mode throws). **`moengage-pixel.ts` still has this defect**, and worse: its `distinct_id` falls back `external_id ?? email` and never to phone, so a phone-only KwikPass shopper gets no identity at all, and it calls `destroy_session()` on an identified→anonymous transition so a transient PII gap tears down the session.
- **2026-07-26** — ⚠️ **Do NOT copy `admin-moengage` / `admin-posthog` for the storefront install instruction — they are superseded.** They still say paste a raw `<script … defer></script>` into `<head>` and point at `apps/<merchant>/lib/pixelConfig.ts`. `docs/agent/changes/pixel-install-ux/SPEC.md` deliberately replaced that with a `next/script` tag — `<Script src=".../<slug>/sdk/<merchantId>.js" strategy="afterInteractive" />` in `src/app/layout.tsx` plus `"<slug>-ratio": {},` in **`src/config/pixelConfig.ts`** — and explicitly fixed `_template-admin` "so future scaffolds inherit the correct pattern". moengage/posthog were never migrated. **Correct references: `_template-admin`, `admin-google`, `admin-loyalty`.** Also: the `pixelConfig` key must equal the pixel's registered `name` (`<slug>-ratio`) or the PixelRuntime silently never activates the SDK — no error on either side.
- **2026-07-25** — ⚠️ **Webhook signature header is contradictory and it affects EVERY vendor.** `core/webhooks/webhook-signature.guard.ts` reads `x-ratio-hmac-sha256`, but the 2026-06-18 entry below (from a real delivery) says deliveries carry `x-openstore-signature`. An absent header is skipped **only** when `NODE_ENV !== 'production'` **or** `WEBHOOK_SIGNATURE_OPTIONAL=true` — so if the platform really sends `x-openstore-signature`, production either **401s every delivery** or is silently running **unverified**. Settle it against a real delivery's headers before any go-live; both entries stay until then.
- **2026-07-25** — The platform has **TWO webhook registries and they disagree** — scope webhook work off both, never one. `admin/webhook-setup/event-definitions` = **master catalog** (21 events / 6 categories, incl. `customers/create|update|delete`) and is what the merchant dashboard renders; `admin/webhook-setup/event-types` = **synced registry**, deliverable today (18 — missing all 3 `customers/*`); `admin/webhook-setup/status` states the drift outright (`eventTypeCount` 18 vs `expectedEventCount` 21). A catalog-but-unsynced topic needs `POST admin/webhook-setup/sync` (an **ops** action), not platform development. Reading only `event-types` produced a wrong CleverTap scope twice. Verified absent from **both**: `checkouts/*`, `fulfillments/*`, `draft_orders/*`, refunds — those are real platform asks. `orders/paid`, `orders/fulfilled`, `orders/partially_fulfilled` **do** exist (don't assume the Fulfillment/Refund-module caveats in older product PRDs still hold). Apps self-register via `POST /api/v1/app-webhooks` `{eventName, webhookUrl, secretKey?, customHeaders?}`.
- **2026-07-15** — The Ratio dashboard iframes the app admin **in the viewer's browser**, so a `localhost` ADMIN_BASE_URL works single-machine (the delhivery dev pattern) — but platform→app **webhooks come server-side** and never reach localhost. Publishing for other people needs public URLs; with one static ngrok domain, `SERVE_FORMS_ADMIN_DIST` (opt-in, main.ts) mounts the built admin at `/admin-forms/` so one origin serves API + admin (hash routing ⇒ no SPA rewrites).
- **2026-07-15** — ngrok **free tier intercepts EVERY browser-UA request** (even `Accept: application/json` fetches) with its warning page unless `ngrok-skip-browser-warning` is sent. forms-sdk sends it only for `*.ngrok-free.*` API bases; the public-CORS allowlist must include the header or preflight fails. Plain `<script src>` can't carry it — demo pages fetch+inject. Vanishes on real hosting.
- **2026-07-15** — Nest registers no OPTIONS routes, so CORS **preflight to `/public/v1/*` 404s** and `enableCors` (origin-checker + credentials) can't do wildcard for shopper-facing endpoints. Fastify `onRequest` (answer OPTIONS 204) + `onSend` (stamp `ACAO:*`, strip allow-credentials) hooks scoped to `PUBLIC_SUBMIT_RE` in main.ts is the pattern. Sandbox ecosystem base told by platform team: `https://api-gw-v4.dev.gokwik.in/sandbox/aes`.
- **2026-06-26** — Wizzy's search/autocomplete (`api.wizsearch.in/v1`) are **public** endpoints: auth = `x-store-id` + a **public** `x-api-key` only, CORS wildcard, and the store **secret** is explicitly forbidden on them (only the catalog write endpoints need it). So a storefront SDK can call Wizzy **directly from the browser** — no backend proxy needed. The public-config endpoint must never return the secret.
- **2026-06-26** — For an embeddable SDK with a hard size budget (`packages/wizzy-sdk`, ≤10KB widget), import shared Zod schemas as **type-only** (`import type …`) so Zod is erased at build and never bundled; do runtime validation on the backend. Also ship the overlay and the faceted results page as **separate** ESM bundles (the loader injects the heavy results bundle only on the results route) to keep the always-loaded overlay small.
- **2026-06-26** — Playwright E2E sharing one static server + the same `page.route` mock patterns across specs flakes under parallel workers (intermittent navigation timeouts). Run it serial: `fullyParallel:false, workers:1, retries:1`.
- **2026-06-22** — Ratio product/variant prices are **integer PAISE (minor units)** — divide by 100 for GMC. Verified against a **live `products/update` webhook** (an OSMO combo: `price:155900` / `compare_at_price:209800` = ₹1,559 / ₹2,098; ₹155,900 would be absurd). This **re-confirms the original 2026-06-08 paise finding** and **reverses the 2026-06-18 "rupees" note**, which was based on *synthetic* test fixtures (`29.99`, `199.99`), not real data. `paiseToMajor` applies in BOTH `parseWebhookProduct` and `parseRestProduct`. ⚠️ The Meta catalog transformer was NOT audited for this — check before trusting Meta prices.

- **2026-06-18** — Real webhook delivery envelope is `{ event_type, merchant_id, product }` — there is **no top-level delivery id or timestamp** (resolves google TRD R1). Core dedupes by deriving `<event_type>:<product.id>` into `webhook_log.ratio_webhook_id`, retry-windowed on `received_at` (~3h) and resting on idempotent handlers — a permanent unique key would wrongly skip a legitimate second update to the same product. Signature header is `x-openstore-signature: sha256=<hex>`.
- **2026-06-18** — The platform exposes products in **two different field shapes**: REST `GET /products` is camelCase (`name`, `description`, `productType`, `inventory.quantity`, `images[].src`, `variants[].sku`) wrapped in `{ success, data[], pagination }`; the webhook `product` is snake_case (`title`, `body_html`, `product_type`, `warehouseQt[]`, `images[].url`, `variants[].variant_id`/`sku_id`, `option1/2/3`). Needs separate normalizers (`parseRestProduct` / `parseWebhookProduct`).
